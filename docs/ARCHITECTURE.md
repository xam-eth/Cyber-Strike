# Architecture

Start here if you are new to this repository. It answers three questions: where
everything lives, what a file is allowed to import, and where a change of yours
should go. Everything below is either generated from the code or enforced by a
check, so it cannot quietly go stale — see [Keeping this document
true](#keeping-this-document-true).

For the selected game direction and active gameplay scope, read
[`GAMEPLAY_DESIGN.md`](GAMEPLAY_DESIGN.md). For task sequencing and quality
gates, read [`DEVELOPMENT.md`](DEVELOPMENT.md). For documentation authority and
conflict handling, start at [`README.md`](README.md). This document governs code
placement; it does not approve new gameplay systems.

---

## The layer rule

Four layers, lowest first. **An import may only point to a lower layer**, or
sideways inside the same module:

| Layer | What belongs there |
| --- | --- |
| `core` | Plumbing nothing gameplay-specific depends on: audio, model fitting, the preferences read model, the muzzle-flash component, and the stateless content-load adapter. |
| `systems` | Rules that drive the game: player, camera, waves, progression services, and the player's weapon handling (`weapon_controller.gd`). |
| `content` | Things the game is *made of*: weapons, enemies, worlds, effects. Data (definitions, `data/` folders) is free for anyone to read. |
| `ui` | Screens. Split into `hud/`, `menus/`, `settings/`, and shared `design/` (tokens, theme, widgets). |

Two consequences worth knowing before you move a file:

* **The HUD and the menus must not import each other.** They are two screens; a
  HUD that reaches into menu-stage code cannot be previewed or shipped on its
  own. Shared modules (`design`, `settings`) are exempt.
* **Content modules do not reach into each other's internals.** Cross-module
  reads are allowed into `data/` and `*_definition.gd` only.
* **Replaceable visual assets cross one dynamic boundary.** World, hero/enemy,
  and held-weapon paths resolve through `scripts/integration/content_module_loader.gd`.
  Core scenes do not preload contributor assets; a failed load returns a reason
  and the owning domain keeps its fallback. Package intake and its limits are
  specified in [`CONTENT_IMPORT.md`](CONTENT_IMPORT.md).

Three files are deliberately classified against their folder, because the
folder rule would otherwise be wrong. Each has the reason next to it in
[`tools/check_architecture.py`](../tools/check_architecture.py):

| File | Classified as | Why |
| --- | --- | --- |
| `scripts/weapons/weapon_controller.gd` | `systems` | It is the player's weapon handling — cooldowns, ammo, switching — not content. |
| `scripts/effects/muzzle_flash.gd` | `core` | A component the player scene owns at `VisualRoot/WeaponSocket`, like `scripts/visual/`. |
| `scripts/ui/settings/aegis_preferences.gd` | `core` | The preferences *model*; systems, content and every screen read it. Only the panel that edits it is screen code. |

## Where does my change go?

| You are adding… | It goes in… | And you must… |
| --- | --- | --- |
| A weapon | `scripts/weapons/` — a `WeaponDefinition`, a projectile, and its effects (effects that only a weapon uses live with the weapon) | register it in `ProgressionService.COSTS` if it unlocks, and add a smoke test |
| A world prop | **nowhere in GDScript** — `tools/asset-forge/src/worlds/roles.js` | add a real GLB from `game/assets/world/real/` to the role; run `node tools/asset-forge/gate/world_shot.mjs` (it fails on any mesh that is not a real asset) |
| A zone or district | `tools/asset-forge/src/worlds/{frostline,verdant,emberfall}.js` | keep coordinates in sync with the Godot zones, then rebuild the affected mission GLB and re-stage it |
| A HUD element | `scripts/ui/hud/` | read from `HudState`; never write back to it — the UI reads from systems and does not drive them |
| A menu page | `scripts/ui/menus/stage_*.gd` extending `MenuStage` | register it in `front_end.gd`'s `STAGE_SCENES`; give it a primary action so Enter works |
| An enemy | `scripts/enemies/` + `resources/enemies/` | register its scene and gameplay role in an `EnemyDefinition`, and add a smoke test |
| An external World/Character visual package | The contributor's disjoint source package, then `game/content/{worlds,characters}/<id>/` through the importer | follow [`CONTENT_IMPORT.md`](CONTENT_IMPORT.md); never directly edit another domain or add runtime package scripts |
| Activation of a staged package | The existing internal definition/adapter and registry | keep Gameplay/Core behavior unchanged unless separately approved; run module-isolation and domain smoke tests |
| Anything | anywhere | run `./scripts/dev_check.sh` before you push |

## Keeping this document true

* The module map is generated by `python3 tools/module_map.py` from the tree,
  using the same classification as the boundary checker, so the two can never
  disagree. Edit it by re-running the tool, not by hand.
* `./scripts/dev_check.sh` fails if the map is out of date or if an import
  crosses a boundary. Both are the same class of error: the code moved and the
  description of the code did not follow.

## What has to pass before a merge

```bash
./scripts/dev_check.sh                    # lint, format, static calls, boundaries, docs, test inventory
./scripts/run_smoke_tests.sh              # current headless Godot smoke inventory
node tools/web_qa.mjs --tour              # boot the Web build, enter gameplay, capture the tour
python3 tools/check_payload.py web/index.pck  # no tests or QA code in what ships
```

The web QA is the check that catches what headless tests cannot: it plays
through the front end to the gameplay scene and captures frames. It needs the
committed preview payload, which is why `web/index.wasm` and `web/index.pck`
are real files in the repository and not LFS pointers.

### Why the static-call check exists

`tools/check_static_calls.py` (step 4 of `dev_check.sh`) compares every
`SomeClass.some_method(` call site against the callee's real declaration,
across files, following `extends` chains and `const X = preload(...)` aliases.

It was added because commit `0884658` — the phase-2 zone split — passed
`gdlint`, `gdformat`, the project doctor and the module map while the game
could not load at all. The zone file had lost its `static` keyword:

```gdscript
NeonFrontierArena.build_central_arena(self)   # build_central_arena was not static
```

Godot rejects that with `Cannot call non-static function ... on the class ...
directly`, drops the whole world script, and 3 of 26 smoke tests fail with
symptoms (a missing reactor, missing ramps) that point nowhere near the cause.
The call is legal syntax, the method exists, and the file is referenced — only
the *static-ness* of the callee is wrong, and that lives in another file. No
single-file linter can see it, which is why this check reads both sides.

Comments and string literals are stripped before scanning, so a class name in a
`##` doc comment is not a call; `tools/tests/test_static_calls.py` holds the
negative controls, including the exact regression above.
