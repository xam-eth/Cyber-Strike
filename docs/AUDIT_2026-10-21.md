# Structural audit — 2026-10-21

Purpose: before anything is deleted, moved or renamed, establish with evidence
what exists, what is alive, what is dead weight, and what blocks a clean
handover. Every number below was produced by a command run against this
checkout at commit `4d585b5`; the commands are quoted so they can be re-run.

Nothing has been changed by this audit. It is a measurement pass.

---

## 1. Method

| Question | How it was answered |
| --- | --- |
| Is a file alive? | Built a corpus of every `.gd/.tscn/.tres/.json/.cfg/.py/.sh/.mjs/.md` file, then for each file under `game/` looked for (a) its `res://` path, (b) its `uid://` (read from the 28 `.uid` files), (c) its bare filename, (d) its `class_name`. A file is only reported dead when all four miss. |
| Is there a dependency cycle? | Built a script-to-script graph from `preload`/`load`/`class_name` references, then DFS for back edges. **Comments and string literals are stripped first** — see §6. |
| What ships to players? | Parsed `web/index.pck` (Godot PCK v4, engine 4.7.2) and searched the payload for `res://` paths. |
| What does CI do? | Read `.github/workflows/godot-ci.yml` end to end. |
| How heavy is the repo? | `du`, `git ls-files`, `git log -- <path>` counts. |

## 4. Finding 1 — the repository is 80 % build history

`web/index.pck` (35.6 MB) has been committed **19 times**, and CI regenerates
it on every push and uploads it as an artifact anyway. `web/index.wasm` is
39.5 MB. The two committed payloads are 75 MB of the 210 MB working tree and
the overwhelming majority of the 169 MB `.git`.

Consequence for handover: a fresh clone downloads ~170 MB of which most is
superseded binary history nobody will ever build from. Fix: stop committing
`web/` (CI artifact + release asset, or Git LFS), then let the history alone
(rewriting it is destructive and out of proportion).

Two unrelated 42 MB of binaries sit at the repository **root** rather than in
`source-assets/`: `HERO+3d+model.glb` (24.4 MB) and
`futuristic gun 3d model.glb` (17.3 MB, spaces in the filename).

## 5. Finding 2 — the test suite and QA tooling ship to players

Parsing the exported payload:

`tools/check_payload.py` reads the PCK directory itself (the v4 layout was
verified against `core/io/file_access_pack.cpp`, not guessed):

```
files in web/index.pck : 772
  res://tests/         : 52 entries, 206 KB
  res://scripts/       : 138
  res://assets/        : 250
  res://.godot/        : 287
```

The 52 test entries are the 26 scripts compiled to `.gdc` plus 26 `.remap`
files. There is **no `exclude_filter`** on either export preset, so all 8,141
lines of test code ship in the web build and would ship in the APK.

`scripts/qa/world_tour.gd` (a keyboard-driven review camera) ships too, and is
additionally instanced as a node inside `scenes/main.tscn` — QA code in the
shipped game scene. It is passive until F10 is pressed and the browser QA
script uses it to photograph the real build, so it is reported as a finding
rather than deleted; moving it into its own scene, excluded from release
exports, is phase 1 work.

The payload also carries **243 `.import` files**.

**Correction, 2026-10-21, by the same person who wrote the paragraph that used
to be here.** The original text called those 243 files "editor metadata in a
player's download" and implied they should be filtered out. That was wrong, and
`tools/check_payload.py` failed the build on them until today. Reading the
exporter properly:

* `editor_export_platform.cpp:1374` — `_edit_filter_list(paths, "*.import", true)`
  does remove `.import` from the source file list, and the comment says why:
  *"Ignore import files, since these are automatically added to the jar later
  with the resources."*
* `editor_export_platform.cpp:1632` and `:1699` — the exporter then writes each
  imported file's `.import` back **rewritten**, with `[remap] path` pointing at
  the converted resource under `.godot/exported/`. It goes through the save
  proxy, which does not apply export filters, so `exclude_filter="*.import"`
  could not have removed them anyway.
* `core/io/resource_importer.cpp:46` and `:331` — `ResourceFormatImporter`
  opens `p_path + ".import"` on load and on path resolution. Without it the
  pack cannot load a single imported asset.

So the `.import` files are required runtime data, not editor metadata. The check
now reports them and never fails on them. A gate that fails on something
mandatory is a gate people learn to ignore, which is the whole reason this
document exists.

### 5.1 Resolved 2026-10-21 — the tests now live outside the project

`exclude_filter="tests/*"` (phase 0) was the wrong fix on its own: a filter is a
setting, and a setting can be dropped by the next hand-edit of a preset. The
tests were moved to `tests/` at the repository root, outside `game/`, so Godot
cannot see them and cannot pack them — by construction, not by configuration.

Proof, measured on a re-exported payload rather than argued:

```
before: 772 files, 35,639,620 bytes   (52 test entries, 206 KB)
after : 720 files, 35,423,608 bytes   (0 test entries)
```

`scripts/run_smoke_tests.sh` and `scripts/export_android_debug.sh` now pass the
absolute path to `--script`; Godot accepts a script outside the project
directory and `preload("res://...")` inside it still resolves against
`--path game`. Verified by running the whole suite from the new location:
**26 passed, 0 failed.**

Two consequences worth recording:

* The 26 `.uid` sidecar files were deleted with the move. They only mean
  something inside `res://`; outside the project they are dead weight.
* `tools/project_doctor.py` went from 39 warnings to 29. The ten that
  disappeared were all "test script is not referenced by anything" — which was
  true then and is true now, and was never a defect. Keeping the tests inside
  the project made the doctor noisier and therefore easier to ignore.

## 12. Three defects found in the project's own tooling

### 12.1 CI has been failing, and nothing was watching

`gh run list` on `arena/e8e7ed65-cyber-strike`: the last **five** pushes are
`completed / failure`, all in the same job — *Static checks (gdtoolkit +
project doctor)*. The engine smoke tests and the web preview were green, which
is why it went unnoticed.

Root cause: `tools/project_doctor.py` compares a script's `extends` against the
node type it is attached to, but only one level deep. Every menu stage is
`extends MenuStage` on a `Control`, and `MenuStage` is a `class_name` script
that itself extends `Control` — so the doctor reported 9 failures that do not
exist, `dev_check.sh` exited 1, and the job went red:

```
fail  script base 'MenuStage' cannot be attached to node type 'Control' (node 'BootStage')
```

Fixed by resolving `class_name` chains down to a built-in type before the
comparison. Two negative controls: a synthetic project with a `Control` script
on a `Node3D` node still fails, and a `extends MyBase` where `class_name MyBase
extends Control` now passes.

A second latent bug surfaced while testing that fix: the doctor's `extends`
regex only matched `extends` at the start of a line, so `class_name
ScifiKitLibrary extends RefCounted` — one line, perfectly legal GDScript, used
in this project — was parsed as having no base class at all, and every check
that compares one silently skipped those scripts. Also fixed.

For a handover this is the most important finding in the document: a new owner
clones the repository, sees a red pipeline on `main`, and has no way to tell
that the game is fine and the checker is wrong.

### 12.2 A gate added in an earlier session broke the tooling self-tests

The `fileSizes` check added to `tools/verify_web_build.py` (declared size vs.
size on disk) is correct and worth having, but the unit-test fixture in
`tools/tests/test_web_preview.py` hard-coded `index.pck` as 100 bytes while
writing 516, so **2 of 23 tooling self-tests had been failing** and
`dev_check.sh` never surfaced them separately. The fixture now builds its
`fileSizes` map from the files it actually writes, with an opt-in
`declared_pck_size` so the tests can break it on purpose — and two tests were
added for the mismatch and missing-map cases. 25 tests, all passing.

The lesson for the remaining phases, stated plainly: a check that is added but
not run in CI is decoration. Both new checkers below are wired into
`scripts/dev_check.sh`, which CI already runs.

### 12.3 The browser QA's world-tour mode has been photographing the menu

Found on 2026-10-21, on the first run of the browser QA after installing
Chromium here (`@sparticuz/chromium` 153.0.0 + `puppeteer-core` 24.31.0, both
already pinned in `tools/package.json`; the binary comes from the npm tarball,
so no CDN is involved).

The boot check itself is good news, and it is real evidence: the WebAssembly
preview boots in a real Chromium at 1280x720 and 390x844, Godot reports no
script or parse errors, WebGL 2 is alive, and the 14 sounds synthesise in
160-370 ms. Four out of four page/viewport combinations pass. Gate G5, "the
preview path still runs", is satisfied.

`--tour` is the part that does not do what it claims. It captures eight frames
and reports "world tour captured frames", but frames 4 to 8 are byte-identical
(same md5), and an instrumented build shows why: the front-end stops at stage
CHAPTER. BOOT → LOADING → CINEMATIC → CHAPTER, and no further. Twenty-two
clicks on the canvas centre over 45 seconds did not advance it, and **zero**
key events reach the review rig, because the rig is created by `main.tscn` and
the game never leaves the menu. The eight "tour frames" are menu frames.

Two things make this a defect in the tooling rather than in the game:

* The QA prints a line reading `world tour captured frames` and exits 0. A pass
  that means "I took eight screenshots" is worse than a failure: nobody looks
  at the frames.
* It is not a regression from the restructuring. Rebuilding the pack from
  `8294bd4`, where `WorldTour` was still a node inside `main.tscn`, produces
  the same frame pattern (frames 4-8 identical). The rig was never reachable
  from the browser either way.

Any QA mode that assumes gameplay — `--tour`, `--menus`, `--encounter` — has
therefore been measuring the front-end, and their screenshots should be treated
as evidence about the menu only.

**2026-10-21, later the same day: two fixes attempted, neither shipped.**

The check now fails loudly instead of passing falsely, which is the part that
matters. Getting the pass to actually reach gameplay did not survive contact
with measurement:

*1. Print the primary button's rect and click it.* Each stage would announce
`MenuCTA: x,y,w,h in <viewport w>,<viewport h>` from `MenuStage.relayout()`.
Measured result: the button's `get_global_rect()` is degenerate while the stage
lives inside the front-end's viewport — `0,0,74,56`, where 56 is the enforced
minimum height and 74 is the unstyled width of the label, and the position is
never set. Deferring the call to the end of the frame and retrying for 120
frames changed nothing. The game change was reverted rather than shipped as an
affordance that does not work.

*2. Walk the focus ring.* Keyboard navigation does work — measured: at the
CHAPTER stage one Tab followed by Enter reaches DASHBOARD. Escaping, then
Tab×k followed by Enter for k = 1..8, repeated over four passes, never reached
the gameplay scene; the selection screens have more focus stops than blind
guessing finds, and a wrong Enter opens the armory or the settings panel.

The next thing worth trying, not attempted: have each stage call
`grab_focus()` on its primary action when it is entered. `ui_accept` then
activates the focused button, so the journey would advance on a single Enter
per stage with no coordinates and no guessing — and a menu that opens with its
primary action focused is better for keyboard players too, not just for the
QA.

### 12.4 What actually got the journey moving (fixed, measured)

`grab_focus()` was tried next, as §12.3 predicted, and on its own it was not
enough. Two measurements explain why, and they contradict each other:

* In a headless engine run (`--script`) it works: the primary button owns GUI
  focus, and a synthetic `ui_accept` moves BOOT -> LOADING -> CINEMATIC.
* In the browser it does nothing. `Control.grab_focus()` refuses unless the OS
  window already owns keyboard focus — Godot's own error is *"Can't grab focus
  on control outside the focused window"* — and a freshly loaded web page is
  exactly that case. Clicking the canvas first does not retroactively help the
  stage that was built before the click, which is why Enter advanced CHAPTER
  (after a Tab) and then stalled at DASHBOARD.

The fix is to stop depending on GUI focus: `menu_stage.gd` now also handles
`ui_accept` at the scene level (`_unhandled_input`) and emits the primary
button's `pressed` signal. When a button *does* hold focus the GUI consumes the
event first, so this never double-fires; when nothing holds focus the stage
still answers Enter. `stage_chapter.gd` calls `super._unhandled_input(event)`
so its click-to-continue fallback survives. This is a real improvement for
keyboard and gamepad players, not only for the QA rig: a menu that answers
Enter with its primary action is what every other screen in the game does.

Measured after the change, `node web_qa.mjs --tour --page /web/index.html`:

```
  ok   front-end journey reached the gameplay scene
  ok   world tour frames differ (8 distinct of 8)
  /web/index.html @ 1280x720 -> PASS (177.2s)
```

The eight frames are 130-243 KB each with a per-channel stddev of ~27 and
870-1310 distinct colours at 80x45, i.e. rendered content, not black frames.
This is the first automated pass that has reached the gameplay scene at all.

### 12.5 The web preview payload must not be under LFS (regression, fixed)

Somewhere in this session `web/index.pck` and `web/index.wasm` were added to
`.gitattributes` as LFS-tracked, and the committed `web/index.wasm` became a
133-byte pointer. The preview then died on load, and because the failure is
downstream of the engine every check in the run failed with it:

```
CompileError: WebAssembly.instantiateStreaming(): expected magic word 00 61 73 6d, found 76 65 72 73 @+0
```

Two things make that unrecoverable rather than merely inconvenient: CI checks
out with `actions/checkout@v4` and no `lfs: true`, so the job that runs
`tools/web_qa.mjs` against `web/index.html` gets the pointer as well; and there
is no git-lfs in this sandbox, where a `filter=lfs` attribute makes `git add`
fail outright. The payload is the one thing a bare clone has to be able to
open, so it is now outside LFS, the same rule that already excluded
`game/assets/**`. Both files are verified real after the fix:
`web/index.wasm` is 39,514,754 bytes starting `00 61 73 6d`, `web/index.pck`
is 35,427,496 bytes starting `47 44 50 43`.

### 12.6 The LFS rules were fiction, and CI paid for it

The web-preview job's "Commit the payload and templates" step failed on two
consecutive runs. Its log cannot be read from this sandbox, so the workflow
was taught to annotate the worktree state before it gives up; the annotation
came back with hundreds of modified files that nobody had touched:

```
[notice] Payload commit
    worktree= M qa-evidence/combat-touch-v2/01-explore.png| M qa-evidence/...
[warning] Payload push retry 1..3   (the same list)
[failure] Preview push failed
    M source-assets/characters/hero/hero_rigged_source.glb| ...
```

Those are phantom modifications, and they are what a mismatch between
`.gitattributes` and reality looks like. Measured over every tracked file:
**of the 239 files the LFS rules covered, exactly one was an LFS object**
(`3DScifiStarterKitFree.zip`). The other 238 were ordinary blobs — a PNG
starting `89 50 4e 47`, a glTF starting `glTF` — because the migration that
was supposed to move them never ran. On a machine with git-lfs the clean
filter turns each real file into a pointer, which never equals the raw blob in
HEAD, so `git status` reports them modified forever and `git rebase` refuses
to start. Without git-lfs the filter is inert, which is why it went unnoticed
here.

Two consequences, one of them sharp:

* CI (which does have git-lfs) saw a permanently dirty worktree, so the step
  that commits the freshly exported preview could not rebase or push. Three
  retries, three failures, and the real export templates never got published.
* The next `git add` of any of those 238 files would have replaced 35 MB of
  evidence images with a 133-byte pointer. A plain clone would silently lose
  them, and nobody local would see it coming.

Fixed by narrowing `.gitattributes` to what is actually in effect (`*.zip`)
and writing the rest down as intent with the reason it is not enabled. The
files themselves are untouched: 238 real blobs stay real blobs. Also untracked
`engine/web_templates/*.zip`, which the catch-all `*.zip` rule had turned into
the same kind of pointer — the templates exist so a local export needs no
1.2 GB download, so a pointer defeats their only purpose.

### 12.7 A note on reading CI from this sandbox

Logs cannot be fetched here: `gh run view --job <id> --log` reaches
`results-receiver.actions.githubusercontent.com`, which is outside the
allowlist, and `gh api .../rerun` answers 403 for this token. A failed job
therefore has to be diagnosed from the annotations the workflow writes (which
is why the export step already posts a digest of its log) and from the job
step list, not from the log. Worth knowing before the next red run.

### 12.8 The boundary checker was measuring a dirty tree

After a sandbox reset the working tree keeps the base commit's files as
untracked leftovers (`git reset --hard` only removes what is in the index), and
`tools/check_architecture.py` walks the filesystem rather than `git ls-files`.
The result: it reported 106 scripts, 230 dependencies and 10 violations, two of
which (`ui/hud` → `ui/menus/hud_editor.gd`) did not exist in the tracked tree at
all — they were a stale copy of a file that had already moved into `ui/hud/`.
Cleaned up, the same check reports 71 scripts, 169 dependencies and 8.

Worth writing down because the failure mode is quiet: a stale duplicate does
not break anything, it just adds findings that look like architecture debt
until someone notices they are ghosts.

Of the 8 real ones, 5 were projectiles importing their impact effects. Those
three effect scripts are used by nothing but the weapon projectiles, so they
moved into `scripts/weapons/` — the boundary now follows usage instead of being
declared against it. Two more were honest misclassifications now written as
per-file rules with reasons: `weapon_controller.gd` is a system (it is the
player's weapon handling), and `muzzle_flash.gd` is core (a component the
player scene owns, like `scripts/visual/`). The last, `aegis_preferences.gd`,
is a read model that systems, content and every screen consult, so it is core
while the panel that edits it stays in `ui/settings`.

The baseline is now empty and `dev_check.sh` runs `--strict`, so a new boundary
violation fails instead of joining a list nobody reads.
